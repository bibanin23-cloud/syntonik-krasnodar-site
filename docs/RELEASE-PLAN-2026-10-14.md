### Pages подтверждены; повторная проверка перед выпуском

Скриншот владельца подтверждает GitHub Actions, `syntonik-krasnodar.ru` и включённый HTTPS. Единственное ожидание в интерфейсе — «Проверка DNS в процессе». Ниже порядок повторной проверки непосредственно перед выпуском, без изменения настроек.

1. Открыть [репозиторий](https://github.com/bibanin23-cloud/syntonik-krasnodar-site).
2. Нажать «Настройки» (Settings). Если вкладка скрыта, открыть дополнительное меню вкладок.
3. В левой панели открыть «Страницы» (Pages), раздел «Код и автоматизация».
4. В «Сборка и развёртывание» прочитать поле «Источник». Для подтверждённого workflow ожидается GitHub Actions. Если показан другой источник, остановиться и сообщить фактическое значение; самостоятельно не переключать.
5. Прочитать «Пользовательский домен»: ожидается `syntonik-krasnodar.ru`.
6. Прочитать состояние «Принудительное использование HTTPS». Записать эти три значения или предоставить видимый скриншот без секретных настроек.

Действующий сайт отвечает 200 по HTTPS; www и HTTP перенаправляются 301 на основной HTTPS-домен. Это подтверждено сетевой проверкой, значения настроек — скриншотом. Перед выпуском обновить страницу и дождаться успешного внутреннего DNS-статуса GitHub; не менять DNS ради жёлтого индикатора. При собственном Actions workflow CNAME-файл не нужен: [GitHub Docs](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/troubleshooting-custom-domains-and-github-pages).

### Подтвердить Apps Script отдельно

1. Открыть [Google Apps Script](https://script.google.com/home) под аккаунтом владельца и найти существующий проект приёма заявок Syntonik. Не создавать новый проект или новую параллельную систему.
2. В проекте открыть «Развернуть» / Deploy → «Управление развёртываниями» / Manage deployments. Найти Web App с URL, совпадающим с `public/lead-config.js` и заканчивающимся `/exec`.
3. Зафиксировать номер активной версии. Важно сравнить именно код этой версии, а не только текущий текст редактора: в Code.gs репозитория есть `normaliseRuMobile`, отдельная колонка Email №13, сохранение прежних статусов в колонке №12 и отключение MAX при MAX_ENABLED=false.
4. Открыть «Настройки проекта» (шестерёнка) → «Свойства скрипта». Проверить MAX_ENABLED с точным значением `false`; Google/Telegram должны использовать существующие свойства. Токены не присылать, не менять и не выводить в лог.
5. Если версия уже соответствует коду — ничего не обновлять. Если отличается — сообщить результат и отдельно согласовать обновление.
6. После разрешения обновлять именно существующее развёртывание: сохранить проверенный Code.gs → «Развернуть» → «Управление развёртываниями» → выбрать существующий Web App → карандаш → «Версия: Новая версия» → «Развернуть». URL `/exec` должен сохраниться. Старую версию записать для отката; deployment не удалять.

Google подтверждает, что обновление Web App требует новой версии существующего deployment; изменение файла редактора само по себе его не обновляет. [Документация Apps Script](https://developers.google.com/apps-script/concepts/deployments).

7. Только после отдельного разрешения выполнить одну помеченную реальную end-to-end заявку со своими данными. Проверить одну строку и одно уведомление, MAX disabled, email/телефон/товар/UTM. Сейчас ни обновление Web App, ни такой тест не выполнены.

- Убедиться, что прежний workflow действительно можно повторно запустить или собрать прежний код. Текстовый SHA без воспроизводимой сборки — недостаточный план отката.

## 4. Что именно согласуется для публикации

Владелец должен ознакомиться с итоговым отчётом и дать явную команду «Публикуй» для точного коммита. Она должна относиться к:

1. Отправке рабочей ветки и PR `site-conversion-update` → `main`.
2. Объединению согласованного PR и автоматическому запуску Pages от нового коммита `main`.
3. Публикации первой статьи, если принято такое решение. Реальная дата назначается в момент выпуска, не задним числом.
4. Любому необходимому обновлению Apps Script — отдельно. Обновление сайта само по себе его не обновляет.
5. Разрешённой одной проверочной заявке после выпуска и оговорённому откату при блокирующем дефекте.

Существующий draft PR архитектуры блога имеет другую ветку и базу. Не объединять его автоматически и не путать с финальным релизным PR. Публикация должна включать только согласованный финальный набор.

## 5. Порядок выпуска — только после разрешения

1. Создать/обновить релизный PR с точным diff и доказательствами проверок; ничего не менять в домене, DNS, настройках Pages и workflow-развёртывания.
2. Выбрать обычный merge commit, чтобы сохранить историю и однозначно откатить релиз. Зафиксировать resulting merge SHA и прежний SHA.
3. После merge в main текущий Pages workflow запускается автоматически. Открыть GitHub → «Действия» (Actions) → «Publish and verify Pages» → новый запуск. Дождаться build → deploy → verify-published.
4. Build использует Node 22, установленный check, sharp 0.35.5, playwright 1.56.1, проверку путей репозитория, затем `actions/configure-pages@v5`. Директория публикации — `dist`; реальный `base_path`, `base_url`, host и indexability берутся из настроек Pages. Не заменять это предположением, что сайт обслуживается из корня repo-path.
5. Подтвердить успешное deploy; в новом deployment должно быть точное release SHA и тот же основной HTTPS-домен. Если build или deploy не прошёл, не менять DNS и не запускать случайные другие workflows.
6. Если deploy прошёл, но verify-published упал, сайт уже мог обновиться. Немедленно провести smoke/откат по согласованному порядку; красный verify не означает, что публикации не было.

## 7. Конкретный откат

Триггеры: недоступная главная, неверный домен/HTTPS, массовые 404/ошибки JS, неработающий каталог/формы, потеря данных заявки, существенное несоответствие согласованной версии.

После заранее согласованного разрешения на откат:

1. Зафиксировать failing deployment SHA и остановить дальнейшие релизные изменения.
2. Предпочтительный путь: создать rollback PR, отменяющий только финальный merge commit (`git revert -m 1 <release_merge_sha>`). После проверки объединить его в main; автоматический Pages workflow публикует восстановленную версию. Не выполнять reset/force push, не откатывать чужие последующие изменения вслепую.
3. Если время критично и разрешён повтор прежнего deployment: GitHub → «Действия» → «Publish and verify Pages» → прежний успешный запуск для записанного старого SHA → «Повторно запустить все задания» / Re-run all jobs. Проверить, что запускается именно старый SHA. Это настоящее развёртывание, сейчас не выполнять. После него оформить согласованный revert в коде, иначе следующий push main может снова вернуть дефектную версию.
4. Если повтор старого run невозможен, собрать и опубликовать зафиксированный старый SHA через согласованный существующий pipeline; не менять Pages/DNS ради обхода ошибки.
5. Повторить HTTPS, навигацию и формы smoke. Если отдельно обновлялся Apps Script и причина в сервере, только по отдельному разрешению вернуть прежнюю version существующего deployment. Не удалять Web App и не перезаписывать Google Таблицу.
6. Убедиться, что restored deployment соответствует записанному рабочему состоянию. Уведомить владельца о результате и сохранить журнал; дальнейшие исправления продолжить в рабочей ветке.
