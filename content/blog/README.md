# Добавление материалов в блог

Блог собирается статически, без CMS и новых зависимостей. Единственный действующий реестр — `content/blog/registry.json`. Общий шаблон — `content/blog/template.html`; генератор — `scripts/blog.mjs`. Главная блога, категории, карточки, оглавления, связанные материалы, SEO и sitemap формируются из реестра.

## Первая статья

Статья о безопасности сохранена в исходном HTML по прежнему адресу `/blog/bezopasen-li-syntonik-dlya-dvigatelya/`. Генератор читает только её утверждённое содержимое через адаптер `legacy-html`. Контрольная сумма защищает оригинал от случайных изменений. Файл не удалять и не преобразовывать в Markdown. Существующие формы и видео берутся из этого же исходника; подвал берётся из главной страницы сайта.

На момент подготовки архитектуры статья существует только в рабочей ветке. Поэтому её статус — `draft`, даты — `null`. Локальный предпросмотр показывает черновики с отметкой; индексируемая production-сборка исключает их страницы, карточки и записи sitemap. Дата публикации указывается только при фактическом выпуске, после отдельного разрешения. Старый `public/blog/publication.json` сохранён как архивный исходник предыдущей реализации и больше не управляет сборкой.

## Новый материал

1. Создать HTML-фрагмент в `content/blog/posts/<slug>.html` с утверждённым текстом. Нужны обычные абзацы, H2/H3, списки, таблицы и ссылки. H1, шапку, подвал, scripts и iframe во фрагмент не добавлять. HTML выбран для сохранения таблиц и инженерных схем без потерь и без подключения парсера Markdown.
2. Добавить запись в массив `posts` реестра. Обязательные поля: `slug`, `title` (H1), `seoTitle`, `description`, `excerpt`, `category`, `author`, `cover`, `coverAlt`, `status`, `datePublished`, `dateModified`, `content`.
3. `content`: `{"format":"html-fragment","file":"content/blog/posts/<slug>.html"}`. Адрес будет `/blog/<slug>/`; существующие slug не менять.
4. Категории: `fuel-consumption`, `engine`, `fuel-quality`, `research`. Автор `igor` уже содержит настоящие сведения и фотографию. Пустые категории автоматически скрываются.
5. `summary` — только согласованный краткий ответ, без придумывания нового инженерного вывода. Если резюме нет, блок «Главное за 30 секунд» скрывается.
6. `featured: true` выделяет основной материал. Желательно назначать главным один материал. `related` — массив slug существующих публикаций; дополнительно выбираются опубликованные статьи той же категории. Черновики, текущая статья и отсутствующие ссылки не показываются.
7. `documents` — массив существующих `/assets/...` ссылок. `videoCaseId` — идентификатор существующего кейса из `public/data/cases.js`; в содержимом используется ссылка с `data-case-video` и существующий URL, без замены приватного параметра. Документы и видео должны присутствовать в утверждённом HTML, генератор не сочиняет дополнительные доказательства.
8. `consultation`: `title`, опциональные `inlineAfter` и `conclusionSection` (ID разделов), `existingFinal`. Для длинной статьи `inlineAfter` размещает один компактный CTA после соответствующего раздела. `conclusionSection` размещает карточку автора после вывода. Если согласованный финальный CTA уже находится в тексте, установить `existingFinal: true`; иначе генератор добавляет его. Формы используют действующий модуль отправки, UTM и адрес страницы; серверная система Google Sheets/Telegram не меняется.
9. Начальный статус — `draft`; даты — `null`. Для фактической публикации указать `published` и реальную `datePublished` в формате `YYYY-MM-DD`. `dateModified` указывается только при содержательном обновлении и не может быть раньше публикации. Не менять даты при каждой сборке.

## Проверка и выпуск

Локальный запуск: `npm start` (порт через `PORT`). Проверки: `npm run build`, `npm test`, `npm run check`. При отсутствии npm можно выполнить соответствующие scripts через pnpm или Node. Дополнительно проверить новую страницу, категорию, документы, оглавление, консультацию и мобильный вид.

Production-сборка: `SITE_URL=https://syntonik-krasnodar.ru/`, `BASE_PATH` пустой, `INDEXABLE=true`; оптимизация изображений — существующий `OPTIMIZE_IMAGES=true`. Черновики исключены, опубликованные материалы индексируются, юридические страницы остаются закрыты. Предпросмотр имеет `noindex,nofollow` и закрытый robots.txt. Canonical всегда указывает на основной домен.

Рабочая ветка — `site-conversion-update`. Не сливать с `main`, не публиковать, не менять Pages/домен/DNS без отдельного разрешения владельца. Перед выпуском согласовать PR и фактические даты. MAX остаётся только обычной ссылкой для общения; отправка заявок в MAX не добавляется.
